# MAM Team Management System

An internal web portal for Mobility Access Modifications to manage team availability, leave requests, manager decisions and synthetic people-operations workflows.

The repository currently contains a deployable foundation and an interactive synthetic workflow demo. It demonstrates full-day and timed leave across one or more dates, sick leave, optional PDF/image evidence, manager approval of employee requests with a coverage calendar spanning three weeks before and after each request, direct manager leave entries, synthetic email previews for the leave workflow, and a privacy-preserving team calendar. It also includes a browser-local People workspace for synthetic onboarding, offboarding and employee check-ins, plus an embedded My profile panel with tenure and essential synthetic support contacts. Recruitment is deliberately excluded.

## Local demo

The interactive demo can build and render without a Supabase connection:

```bash
npm ci
npm run dev -- -p 3001
```

Open `http://localhost:3001`.

Use the top-right profile selector to preview the workspace as HR, the Major Mod manager, the Minor Mod manager or several employees. The intentionally minimal sidebar contains Home, one Leave workspace, the team calendar and People. For managers, Leave contains a clear in-page switch between team requests and the items waiting for their decision; employees only see their own leave. “Pending” counts every pending employee request visible in the current request list, while “To approve” counts only employee requests assigned to the current manager. Managers add their own leave directly to the calendar as approved records and never approve themselves. Approval records show the applicant highlighted in a weekly calendar grid, relevant team leave and a clearly marked synthetic public-holiday example; private reasons never appear there. A person can optionally choose a start time for the first date and an end time for the last date between 6:00 am and 6:00 pm in fixed 15-minute intervals; the demo totals only weekday working-window hours between them.

A request can include up to three PDF or image files of 5 MB each. Files stay only in the open browser session during the no-login demo, disappear on refresh or reset, and are shown only when the profile selector is set to a manager or HR. “Email activity” previews the manager, employee, HR and Accounts notifications generated by requests and decisions; it does not send email, store addresses or use credentials. This is an honest workflow preview, not a security boundary. The versioned staff/auth migration creates a private Supabase Storage bucket and RLS-backed metadata for real manager/HR-only access once authenticated identities are enabled.

When `NEXT_PUBLIC_SHARED_DEMO=true` and the public Supabase variables are configured, submissions, decisions and resets are shared in realtime across open browsers. “Reset demo” restores the fixed fake dataset for everyone. The profile selector remains a role simulation, not authentication, so this mode must never contain real staff or leave data.

The People workspace starts with a compact My profile panel, then exposes role-assigned synthetic onboarding and offboarding checklists, task statuses, an illustrative asset/access register, selected evidence filenames, audit entries and readiness outcomes only when needed. Employees can see only their onboarding and check-ins; offboarding is restricted to the simulated HR and relevant manager views. Its Check-ins tab uses the current schedule of 2 weeks, 1 month, 3 months and 5-month probation; prompts are due 3 days, 4 business days, 2 weeks, and 2 weeks plus a final 1 week before the respective check-in. Running a due reminder adds an in-app email preview only. My profile derives a synthetic tenure from the selected profile, can show a subtle anniversary treatment on a configured demo date, and lists only synthetic manager, People and IT contacts. People/profile cases, selected evidence/upload state and reminder activity are browser-local, clear on reset or refresh, do not create accounts or provision/revoke access, and are not shared through Supabase or sent by email.

## Connected development

1. Select the verified MAM Supabase project.
2. Copy the safe template:

   ```bash
   cp .env.example .env.local
   ```

3. Fill the development project URL and publishable key, then set `NEXT_PUBLIC_SHARED_DEMO=true`. Do not add secret/service-role keys to `NEXT_PUBLIC_*` variables.
4. Store the same browser-safe variables in the verified MAM Vercel project for Development, Preview and Production.
5. Apply only the shared synthetic demo migrations. Do not apply the future staff/auth migration until the business rules in `docs/business-rules.md` are confirmed.

## Environment variables

| Variable | Exposure | Purpose |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Browser-safe | MAM Supabase API URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Browser-safe | Modern Supabase publishable key; protected by RLS |
| `NEXT_PUBLIC_SHARED_DEMO` | Browser-safe | Enables the shared synthetic dataset and realtime subscription |
| `NEXT_PUBLIC_APP_URL` | Browser-safe | Exact origin used in authentication redirects |
| `MAM_ALLOWED_EMAIL_DOMAIN` | Server-only | Optional work-email allowlist |

See `docs/environment-management.md` for the full model.

## Deployment order

1. Confirm the MAM GitHub repository and its default branch are the intended deployment source.
2. Select the MAM Supabase organization, review the quoted project cost, then create the project in Sydney (`ap-southeast-2`) unless MAM requires another region.
3. Review and apply the database migration; run Supabase security and performance advisors.
4. Confirm the MAM Vercel project remains linked to the GitHub repository.
5. Add environment variables separately for Development, Preview and Production.
6. Deploy a preview, test sign-in and RLS with synthetic users, then obtain management approval before production.
